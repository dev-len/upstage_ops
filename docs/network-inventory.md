## 1. VPC 개요

| 항목 | 값 |
|------|-----|
| 리전 | `us-east-1` |
| VPC 유형 | AWS 기본(Default) VPC |
| IPv6 | 없음 |

> 기본 VPC를 그대로 사용한다 (PRD 기준). 커스텀 VPC 생성은 하지 않는다.

> [!WARNING]
> **학습용 계정 IAM 제약**: VPC, 서브넷, 라우팅 테이블, IGW 등 네트워크 리소스에 대한 **수정 권한이 없다**.
> 기존 기본 VPC 구성을 있는 그대로 사용해야 하며, 라우팅 변경이나 서브넷 추가/삭제는 불가능하다.
> 이 제약은 Security Group 생성/수정에도 적용될 수 있으므로, Phase 2 착수 전에 SG 관련 IAM 권한을 반드시 확인해야 한다.

## 4. 인터넷 게이트웨이 (1개)

| IGW ID | 설명 |
|--------|------|
| `igw-05072b8cefd6e2124` | 퍼블릭 서브넷 6개에 인터넷 라우팅 제공 |

- 6개의 **퍼블릭** 서브넷으로 인터넷 라우팅
- 프라이빗 서브넷 라우팅: 0개

> 모든 서브넷이 IGW를 통해 퍼블릭으로 노출된다. EC2 인스턴스에 퍼블릭 IP가 할당되면 인터넷에서 직접 접근 가능하므로, **Security Group 설정이 유일한 접근 제어 수단**이다.

## 4.1 VPC Endpoint (미연결)

VPC Endpoint가 존재하지만, 현재 어떤 서브넷에도 연결되어 있지 않은 상태이다.

| 항목 | 상태 |
|------|------|
| VPC Endpoint | 존재함 (상세 ID 미확인) |
| 서브넷 연결 | ❌ 없음 |
| 수정 가능 여부 | ❌ 불가 (IAM 권한 없음) |

> [!NOTE]
> VPC Endpoint가 서브넷에 연결되지 않아도 현재 아키텍처에는 직접적인 영향이 없다.
> 외부 LLM API 호출 등 인터넷 트래픽은 IGW를 통해 나가므로 정상 동작한다.
> 다만 S3, DynamoDB 등 AWS 서비스 접근 시 VPC Endpoint를 사용하면 비용/성능 이점이 있으나, IAM 권한 제약으로 설정 변경이 불가하므로 현 상태를 수용한다.

## 5. K3S 7노드 배치 시 참고 사항

### 5.1 서브넷 선택

- 기본 VPC의 6개 서브넷은 모두 퍼블릭이므로, 어떤 서브넷에든 노드를 배치할 수 있다.
- 단순성을 위해 **단일 AZ에 모든 노드를 배치**하는 것을 권장한다 (AZ 간 통신 지연 최소화).
- AZ 선택 기준: EC2 인스턴스 타입(`t3.medium`) 가용성, 스팟 가격 등을 고려한다.

### 5.1.1 현재 기준 노드 역할

현재 아키텍처 기준선은 7노드 역할 분리다.

| 역할 | 수량 | 네트워크 관점 메모 |
|------|------|-------------------|
| Server | 1대 | K3S API 진입점 |
| App | 2대 | Ingress 뒤 애플리케이션 워크로드 |
| Metrics | 1대 | Prometheus/Grafana |
| Logs-Traces | 1대 | Loki/Tempo/OTel Collector |
| DB | 1대 | PostgreSQL/Redis |
| LLM-Obs | 1대 | Langfuse Web + Worker |
| ClickHouse | 1대 | Langfuse 분석 저장소 |

> 현재 문서 기준으로는 멀티 AZ 분산보다 단일 AZ 내 역할 분리를 우선한다.

### 5.2 Security Group 설계 포인트

아래 포트를 최소한으로 허용하는 Security Group을 Phase 2에서 정의한다.

| 용도 | 포트 | 방향 |
|------|------|------|
| SSH | 22 | Inbound (관리자 IP만) |
| K3S API Server | 6443 | Inbound (관리자 IP / 노드 간) |
| Kubelet | 10250 | 노드 간 |
| VXLAN (Flannel) | 8472/UDP | 노드 간 |
| Ingress HTTP/HTTPS | 80, 443 | Inbound (전체) |
| NodePort 범위 | 30000-32767 | 필요 시 |

> Security Group 포트 매트릭스 상세는 [아키텍처 §10.2](./architecture.md#102-미결정-보안-항목)에서 미결정 항목으로 남아 있다.

### 5.2.1 7노드 기준 SG 묶음 방향

현재 Terraform 모듈은 `main_node` / `sub_node` 2계층 SG만 제공한다.
7노드 토폴로지에 맞추려면 Phase 2에서 아래 둘 중 하나로 확장해야 한다.

- 옵션 1: 서버 SG 1개 + 공통 워커 SG 1개로 유지하고, 역할 분리는 Kubernetes 라벨/taint로 제어
- 옵션 2: 서버 SG 1개 + 역할별 워커 SG(`app`, `metrics`, `logs-traces`, `db`, `llm-obs`, `clickhouse`)로 세분화

현 시점 권장 방향은 다음과 같다.

- 초기 Terraform: 서버 SG 1개 + 공통 워커 SG 1개로 시작
- 후속 확장: `80/443`, 역할별 inbound, DB 계층 최소 노출 규칙 추가

즉, **Terraform 현재 상태는 7노드 완성형이 아니라 7노드로 가기 위한 최소 검증 단계**다.

### 5.3 IP 용량

- 각 서브넷은 `/20` 블록으로 약 4,091개의 사용 가능한 IP를 제공한다 (AWS 예약 5개 제외).
- K3S 노드 7대 + Pod CIDR을 고려해도 IP 부족은 발생하지 않는다.
