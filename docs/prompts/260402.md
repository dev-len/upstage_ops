# 2026-04-02 프로젝트 초기 구성

## 프로젝트 개요

- **프로젝트 유형**: Ops (인프라 운영 및 자동화)
- **역할**: DevOps (팀 프로젝트)
- **목적**: 학습 및 경험 중심의 인프라 구축 + LLM 서비스를 위한 운영 환경 구성
- **핵심 스택**: AWS, Terraform, K3S
- **서비스 스택 (예정)**: Next.js (Node.js) 또는 FastAPI (Python)

## 환경 제약사항

### AWS 학습용 계정 제한

| 항목 | 상태 |
|------|------|
| AWS 리전 | **us-east-1** (N. Virginia) |
| IAM 사용자/역할 생성 | ❌ 제한됨 |
| 외부 접근 키(Access Key) 생성 | ❌ 제한됨 |
| EC2 인스턴스 크기 | ⚠️ **medium**까지 허용 |
| EC2 인스턴스 수 | 제한 없음 |
| 운영 OS | Ubuntu 22.04 LTS |
| AWS Cloud Shell 사용 | ✅ 가능 |
| Terraform 실행 환경 | Cloud Shell 내부에서 실행 |

> Cloud Shell은 세션 종료 시 `$HOME` 디렉터리만 유지되고 나머지는 초기화된다.
> Terraform binary, provider plugin 캐시 등의 영속성 전략이 필요하다.

## 구현 범위

### 1. 인프라 프로비저닝 (Terraform)

Cloud Shell 환경에서 Terraform을 실행하여 AWS 리소스를 프로비저닝한다.

- **네트워크**: VPC, Subnet, Security Group, Internet Gateway
- **컴퓨팅**: EC2 인스턴스 — `t3.medium` 이하 (K3S 노드용, Ubuntu 22.04)
- **스토리지**: EBS (영구 볼륨용)
- **DNS/접근**: Elastic IP 또는 Route53 (가능한 범위 내)

#### Cloud Shell Terraform 워크플로우

```
[Cloud Shell]
  ├── $HOME/terraform-bin/       # Terraform 바이너리 영속 보관
  ├── $HOME/infra/               # Terraform 코드 (Git clone)
  │   ├── main.tf
  │   ├── variables.tf
  │   ├── outputs.tf
  │   └── terraform.tfstate      # 상태 파일 (S3 backend 권장)
  └── $HOME/.terraformrc         # Provider 캐시 설정
```

#### State 관리 전략

- **로컬 상태**: Cloud Shell `$HOME`에 보관 (단순하지만 협업 불가)
- **S3 Backend**: S3 버킷 + DynamoDB 잠금 (IAM 제한에 따라 가능 여부 확인 필요)
- **Git 기반**: 상태 파일을 Git으로 관리 (비권장이지만 학습용으로 차선책)

### 2. K3S 클러스터 구축

EC2 인스턴스 위에 경량 Kubernetes인 K3S를 멀티 노드로 구성한다.
서버 노드에서 에이전트 노드들을 컨트롤하는 구조.

- **노드 스펙**: EC2 `t3.medium` (2 vCPU, 4GB RAM) — 계정 제한 최대치
- **운영 OS**: Ubuntu 22.04 LTS (us-east-1 AMI 확인 필요)
- **구성 방식**: 서버 1대 + 에이전트 N대 (풀스택 역할 분리)
- **설치 자동화**: Terraform `user_data` 또는 cloud-init 활용
- **Ingress**: Traefik (K3S 내장) 또는 Nginx Ingress Controller
- **인증서**: Let's Encrypt + cert-manager (도메인 확보 시)

#### 노드 구성 (풀스택 역할 분리)

```
┌─────────────────────────────────────────────────────────┐
│                    K3S Cluster                           │
│                                                         │
│  ┌─────────────────┐                                    │
│  │ Server (Master)  │  K3S 컨트롤 플레인                │
│  │ t3.medium        │  etcd, API Server, Scheduler      │
│  └────────┬─────────┘                                    │
│           │                                              │
│  ┌────────┼────────────────┬──────────────┐              │
│  ▼        ▼                ▼              ▼              │
│ ┌──────┐ ┌──────────────┐ ┌──────────┐ ┌──────────────┐ │
│ │Agent1│ │Agent 2       │ │Agent 3   │ │Agent 4       │ │
│ │App   │ │Observability │ │DB        │ │LLM Obs       │ │
│ │------│ │--------------│ │----------│ │--------------│ │
│ │Next/ │ │Prometheus    │ │PostgreSQL│ │Langfuse      │ │
│ │Fast  │ │Grafana       │ │(Langfuse │ │              │ │
│ │API   │ │Loki          │ │ 용)      │ │              │ │
│ │서비스│ │Tempo         │ │          │ │              │ │
│ └──────┘ └──────────────┘ └──────────┘ └──────────────┘ │
└─────────────────────────────────────────────────────────┘
```

> **참고**: 노드 수는 서비스 스택 확정 후 최종 결정한다.
> 최소 구성은 서버 1 + 에이전트 2~3 에서 시작하여 필요 시 확장.

### 3. 텔레메트리 (Observability)

Three Pillars(로그, 메트릭, 트레이스)를 모두 구축한다.
시각화는 **Grafana**로 통일한다.

#### 관측 스택 결정

| 신호 | 도구 | 수집 방식 |
|------|------|----------|
| **Metrics** | Prometheus | 직접 scrape (pull 기반) |
| **Logs** | Loki | OTel Collector 경유 |
| **Traces** | Tempo | OTel Collector 경유 |
| **시각화** | Grafana | 단일 대시보드 |

#### 하이브리드 수집 아키텍처

메트릭은 Prometheus가 직접 pull, 로그/트레이스는 OpenTelemetry Collector를 통해 수집한다.

```
┌─ 각 노드 (DaemonSet) ─────────────────────────────────────┐
│                                                            │
│  [App Pod] ──── OTel SDK ──┐                               │
│                            ▼                               │
│                   ┌─────────────────┐                      │
│                   │ OTel Collector  │                      │
│                   │ (DaemonSet)     │                      │
│                   │                 │                      │
│                   │ Receivers:      │                      │
│                   │  - OTLP (gRPC)  │── traces ──▶ Tempo   │
│                   │  - filelog      │── logs ────▶ Loki    │
│                   │                 │                      │
│                   └─────────────────┘                      │
│                                                            │
│  [App Pod] ◀── scrape ── [Prometheus]  (metrics, pull기반) │
│                                                            │
└────────────────────────────────────────────────────────────┘
                            │
                            ▼
                    ┌──────────────┐
                    │   Grafana    │
                    │              │
                    │ Data Sources │
                    │ - Prometheus │
                    │ - Loki       │
                    │ - Tempo      │
                    └──────────────┘
```

#### 각 도구 역할 상세

**Prometheus (메트릭)**
- Pull 기반: 주기적으로 `/metrics` 엔드포인트 scrape
- ServiceMonitor/PodMonitor CRD로 대상 자동 발견
- AlertManager 연동으로 알림 설정 가능
- 학습 포인트: PromQL 쿼리, recording rules, alerting rules

**Loki (로그)**
- 인덱스 없이 라벨 기반 로그 저장 → 리소스 효율적
- OTel Collector가 Pod 로그를 수집해서 Loki로 전송
- Grafana에서 LogQL로 로그 검색/필터링

**Tempo (트레이스)**
- 분산 추적 백엔드, 오브젝트 스토리지 기반
- OTel SDK가 앱에서 span 생성 → Collector → Tempo
- Grafana에서 trace ID 기반 검색, 서비스 맵 시각화

**OpenTelemetry Collector (수집 레이어)**
- 각 노드에 DaemonSet으로 배포
- 로그: filelog receiver로 Pod 로그 수집
- 트레이스: OTLP receiver로 앱에서 전송받은 span 수집
- 프로세서: 배치 처리, 속성 추가, 필터링
- 익스포터: Loki exporter, OTLP exporter (Tempo)

#### 앱 계측 (Instrumentation)

서비스 스택에 따른 OTel SDK 적용:

| 프레임워크 | OTel SDK | 자동 계측 |
|-----------|----------|----------|
| **FastAPI (Python)** | `opentelemetry-python` | `opentelemetry-instrument` CLI로 자동 계측 가능 |
| **Next.js (Node.js)** | `@opentelemetry/sdk-node` | `experimental.instrumentationHook` 설정으로 자동 계측 |

> 두 스택 모두 OTel 지원이 성숙하여 어느 쪽을 선택해도 무방.

### 4. LLM 관측 (Langfuse)

LLM 서비스 전용 관측은 **Langfuse**를 셀프 호스팅한다.

- **배포 위치**: K3S 클러스터 내 전용 노드 (또는 관측 노드에 동거)
- **의존성**: PostgreSQL (Langfuse 데이터 저장용)
- **기능**:
  - LLM 호출 트레이싱 (입력/출력/레이턴시)
  - 프롬프트 버전 관리
  - 토큰 사용량 및 비용 추적
  - 사용자별/세션별 분석
- **연동**: OTel과 Langfuse를 함께 사용하여 인프라 트레이스와 LLM 트레이스를 Grafana에서 통합 조회 가능

```
[LLM 서비스] ── Langfuse SDK ──▶ [Langfuse Server] ──▶ [PostgreSQL]
     │                                  │
     │                                  └── Langfuse UI (자체 대시보드)
     │
     └── OTel SDK ──▶ [OTel Collector] ──▶ Tempo (인프라 트레이스)
```
